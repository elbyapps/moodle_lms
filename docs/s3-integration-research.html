Moodle ⇄ S3 integration

Research + concrete plan for making S3 a smooth, env‑switchable choice in this repo. Compiled 2026‑05‑19. Focused on tool_objectfs; the in‑house reblibrary plugin is out of scope here and will be addressed separately.

TL;DR

  1. Use tool_objectfs by Catalyst IT — the standard Moodle plugin for moving filedir to S3‑compatible storage. It works with AWS S3, Garage, MinIO, DigitalOcean Spaces, Azure Blob, GCS, Swift. (github.com/catalyst/moodle-tool_objectfs)
  2. Moodle 5 compatibility caveat. The latest stable branch MOODLE_404_STABLE declares $plugin->supported = [404, 405] — it works on Moodle 5 in practice (people are running it), but it doesn't officially claim 5.1 support and there is an open PR (#691) fixing one Moodle‑5‑specific exception. Pin a known commit, not a moving tag.
  3. Make backend selection a single env knob: FILESTORAGE_BACKEND=local|s3. config.php.docker branches on it and forces all S3 settings via $CFG->forced_plugin_settings['tool_objectfs'] — so secrets stay in .env, never in the Moodle DB.
  4. Dev → Garage container. Staging/Prod → external https://storage.reb.rw. Same plugin, different endpoint. Same compose, different env file.
  5. Roll out in two phases, not one: phase A ships local→S3 migration in the background with deletelocal=0 (safe, reversible); phase B flips deletelocal=1 and optionally enables pre‑signed URLs to offload PHP‑FPM bandwidth.

3. tool_objectfs: how it actually works

It's important to understand the model before designing config around it — most "I broke production with objectfs" stories come from people who misunderstood this.

The two‑tier file system

  1. Moodle still writes new files to local moodledata/filedir/<hash[0..2]>/<hash[2..4]>/<hash> via the normal API. Local disk is always the source of truth at write time.
  2. A scheduled task (pusher) periodically scans local files. Files that are older than minimumage and larger than sizethreshold get uploaded to the bucket under a key derived from the same content hash.
  3. A second task (deleter) eventually removes the local copy of any file that's been verified in the remote, but only after consistencydelay has elapsed. Until that point, both copies coexist and reads transparently prefer local.
  4. On read, if a file isn't local, tool_objectfs streams it back from S3 — or, if pre‑signed URLs are enabled and the request comes through Moodle's pluginfile.php, it issues a 302 to a time‑limited signed URL and the browser fetches from S3 directly.

What gets stored in the bucket

Only filedir contents — i.e. files uploaded by users (assignments, course resources, badges, profile pics, mod_resource content, etc.). Caches (moodledata/cache, moodledata/localcache, moodledata/muc), sessions, temp dirs, and the lang cache stay on local disk. That's intentional: those need POSIX semantics and locality.

Concretely, for our deployment that means the named volume prod_elearning_moodledata stays — but it shrinks dramatically because filedir/ (the ~83 GB part) drains into S3 over time.

4. Moodle 5.1 compatibility — the only real risk

Findings from the upstream repo today (2026‑05‑19):

  • Default branch is MOODLE_404_STABLE, last push 2026‑04‑15, version 2026041000, $plugin->supported = [404, 405].
  • The master branch is stale (2021) and labelled DEPRECATED_master in nearby branches.
  • No MOODLE_500_STABLE or MOODLE_501_STABLE branch exists.
  • Open PR #691 — "fix(s3.client): catch AWS UnresolvedAuthSchemeException when testing connection on Moodle 5" — open since 2025‑07‑13, not merged. Indicates Catalyst is aware of Moodle‑5 issues but hasn't shipped a 5.x branch.
  • Active forks (e.g. borrown, rjfarnott/…_R2, CampusTraining) all still track MOODLE_404_STABLE.

What this means for our Moodle 5.1.4 stack

  • Installation will print a "this plugin doesn't support your Moodle version" warning. $plugin->supported is advisory; install proceeds.
  • The Moodle file_system API has been stable since 3.3, so the core integration is very likely to work.
  • Risk is concentrated in: (a) the AWS SDK bundled with local_aws may use deprecated patterns on PHP 8.3+, (b) the "test connection" admin button may hit the bug PR #691 fixes, (c) some admin pages use Moodle UI APIs that changed in 5.x and may render with deprecations.

Mitigation

  1. Pin a specific commit on MOODLE_404_STABLE in moodle-config.json, not the branch tip — so an upstream push can't change behaviour under our feet.
  2. Apply PR #691 as a patch (or use a fork that has it merged) — small, surgical change.
  3. Validate on prodtest with the same Moodle 5.1.4 image and the same Garage version before touching staging.
  4. Keep deletelocal=0 for at least one week in staging. Until you flip that switch, S3 is purely additive — local filedir/ remains a fully working fallback.

5. Proposed design — one env var, three environments

The contract we want for "smooth configuration":

  • One env var FILESTORAGE_BACKEND with values local (default) or s3.
  • All S3 credentials and the endpoint come from the existing S3_* env vars.
  • config.php.docker branches on the backend value and, when s3 is selected, forces every tool_objectfs setting through $CFG->forced_plugin_settings. Forced settings are read‑only in the admin UI — that's the point: secrets live in the env file, never in the database, never in a Moodle export.
  • Compose files don't change shape per environment. Only the .env differs.
  • build.sh clones tool_objectfs + local_aws into moodle_app/public/admin/tool/objectfs and moodle_app/public/local/aws regardless of backend — installed but inert when FILESTORAGE_BACKEND=local.

6.3 config.php.docker — branch on the env

// === Object storage (tool_objectfs) ===
// Backend selector. When 'local', tool_objectfs is installed but inert.
$filestoragebackend = getenv('FILESTORAGE_BACKEND') ?: 'local';

if ($filestoragebackend === 's3') {
    // 1. Hand Moodle's whole file_system over to objectfs.
    $CFG->alternative_file_system_class = '\tool_objectfs\s3_file_system';

    // 2. Force every plugin setting from env. Forced settings are read-only
    //    in the admin UI and are *not* stored in mdl_config_plugins, so
    //    secrets live in .env, not in DB exports.
    $CFG->forced_plugin_settings['tool_objectfs'] = [
        // Generic
        'enabletasks'        => (int)(getenv('OBJECTFS_ENABLE_TASKS') ?: 1),
        'sizethreshold'      => (int)(getenv('OBJECTFS_SIZE_THRESHOLD') ?: 131072),
        'minimumage'         => (int)(getenv('OBJECTFS_MINIMUM_AGE') ?: 604800),
        'deletelocal'        => (int)(getenv('OBJECTFS_DELETE_LOCAL') ?: 0),
        'consistencydelay'   => (int)(getenv('OBJECTFS_CONSISTENCY_DELAY') ?: 600),
        'deleteexternal'     => (int)(getenv('OBJECTFS_DELETE_EXTERNAL') ?: 1),
        'filesystem'         => '\tool_objectfs\s3_file_system',

        // S3 specifics (Garage in dev, storage.reb.rw in staging/prod)
        's3_key'             => getenv('S3_ACCESS_KEY'),
        's3_secret'          => getenv('S3_SECRET_KEY'),
        's3_bucket'          => getenv('S3_BUCKET'),
        's3_region'          => getenv('S3_REGION') ?: 'us-east-1',
        's3_base_url'        => getenv('S3_ENDPOINT'),
        's3_usesdkcreds'     => 0,

        // Pre-signed URLs (off until phase B)
        'enablepresignedurls'  => (int)(getenv('OBJECTFS_PRESIGNED') ?: 0),
        'expirationtime'       => (int)(getenv('OBJECTFS_PRESIGNED_EXPIRATION') ?: 600),
        'presignedminfilesize' => (int)(getenv('OBJECTFS_PRESIGNED_MIN_SIZE') ?: 0),
        'signingwhitelist'     => getenv('OBJECTFS_PRESIGNED_WHITELIST') ?: '',
        'signingmethod'        => 's3',
    ];
}

6.4 Compose — pass S3_* into PHP/cron

The base compose/docker-compose.yml already sets env_file: .env for php and cron, so the variables are already reaching the containers. No compose changes needed for staging/prod — just populate the env file.

For the dev case, compose/docker-compose.dev.yml defines php without env_file override and inherits from base — also fine. The only thing to add to dev is a depends_on: garage-init on php if you want PHP to wait for the bucket to exist before starting (optional; objectfs handles missing bucket gracefully on first task run).

6.5 build.sh — confirm it already supports git plugins with destination

Spot‑check: the existing moodle-theme_elby entry uses the same source: git + destination shape, so adding two more entries is mechanical, not architectural. If build.sh currently hardcodes destinations under theme/, generalise it to honour the destination key.

7. Migration plan + rollback

Phase A — dual‑write (safe, reversible)

  1. Roll out plugin install on prodtest. Confirm: admin UI loads under Site Admin → Plugins → Admin tools → Object storage file system; all settings show as "locked" (forced).
  2. Trigger a manual run of the pusher task: php admin/cli/scheduled_task.php --execute='\tool_objectfs\task\push_objects_to_storage' in the cron container.
  3. Verify objects appear in the bucket. Verify Moodle still serves files correctly when local copy is present.
  4. Promote to staging with the production endpoint storage.reb.rw and a separate bucket moodle-staging (or a prefix). deletelocal=0.
  5. Let it run for ≥7 days. Watch task logs, S3 storage growth, response times.

Rollback in phase A: set FILESTORAGE_BACKEND=local, redeploy. Moodle returns to reading local filedir exclusively. Nothing was deleted.

Phase B — drain local (one‑way)

  1. Flip OBJECTFS_DELETE_LOCAL=1 in staging. cron deleter starts reclaiming local disk.
  2. After local has drained, optionally enable OBJECTFS_PRESIGNED=1 with a whitelist of large‑file extensions to offload PHP‑FPM bandwidth on big downloads.
  3. Repeat for prod. Production filedir/ goes from ~83 GB to "small files + recent uploads only".

Rollback in phase B is harder. Once deletelocal=1 has reclaimed a file locally, the only way back to "local‑only" is to download every object from S3 — possible via aws s3 sync, but slow and storage‑hungry. Treat this flip as a real production change.

8. Operational concerns

8.1 Two endpoints (internal vs public)

PHP talks to S3 server‑side. Browsers only ever see S3 if you turn on pre‑signed URLs. When that day comes, PHP and browsers may need different hostnames:

  • PHP container: https://storage.reb.rw (or http://garage:3900 in dev) — fast path, internal.
  • Browser: https://storage.reb.rw — same hostname is fine here since reb's S3 is internet‑reachable. If you ever put Moodle in a private VPC with S3 on a private endpoint, you'd need to split: PHP signs with the private endpoint, then we rewrite the signed URL to the public one. tool_objectfs doesn't ship that split natively — the cleanest workaround is to always use the public hostname for both.
  • In dev, pre‑signed URLs are off (Phase A), so the dev split between http://garage:3900 (PHP) and http://localhost:3900 (browser) is moot. If you ever enable pre‑signed URLs in dev, set S3_ENDPOINT=http://localhost:3900 so the signed URLs are reachable from the host browser — PHP can reach localhost from inside the container only via host.docker.internal, which is already in extra_hosts, so this works.

8.2 CORS

Required when pre‑signed URLs are enabled, because the browser fetches from a different origin. The dev Garage init script already sets up permissive CORS. For prod at storage.reb.rw, lock AllowedOrigins to your Moodle origin(s) — not *. The Garage prod install doc has the recipe (under "Enable CORS").

8.3 Backups

Today scripts/moodle-backup.sh presumably tars the moodledata volume. Once filedir lives in S3, your backup strategy must include:

  • Bucket replication / versioning on storage.reb.rw, OR a periodic aws s3 sync to a cold bucket. (Garage 1.x supports versioning per bucket.)
  • The DB backup remains the single most important artefact — files are content‑addressed; without the DB, files are orphan blobs.
  • Snapshot of Garage metadata if you self‑host (see docs/garage-production-install.md, metadata_auto_snapshot_interval = "6h").

8.4 Cleanup / orphan files

tool_objectfs ships a "delete orphaned objects" scheduled task that scans for objects in S3 with no matching {files} row. Enable it once you're comfortable; until then, deleted Moodle files stay in S3 forever (cheap insurance during rollout).

8.5 Monitoring

  • Task health: Site Admin → Server → Scheduled tasks. The push_objects_to_storage and delete_local_objects tasks should run on cadence and not pile up failures.
  • Status report: Site Admin → Plugins → Admin tools → Object storage file system → "Object status" gives counts of local‑only / duplicated / remote‑only files. Eyeball this weekly during rollout.
  • S3 5xx rate from Garage / storage.reb.rw — surface as a metric to your existing observability.

8.6 Performance expectations

  • Small file reads served from local stay at local‑disk latency — no change.
  • Files in S3 only: ~10–50 ms added per request for the HEAD+GET, dominated by network. For Moodle's typical small‑file traffic that's not great as a steady state — which is why pre‑signed URLs matter for the long tail of large media downloads.
  • PHP‑FPM memory is unaffected; objectfs streams chunks via the SDK rather than buffering.

9. Garage‑specific notes

  • Region naming. Your .env uses S3_REGION=rw-central-1, but docker/garage/garage.toml declares s3_region = "rw-central-1" for dev — these must match exactly for signature v4 to validate. Production garage at storage.reb.rw presumably also reports rw-central-1; double‑check that's what the public node actually advertises.
  • Path‑style addressing. Garage works with both virtual‑hosted and path‑style, but Catalyst's S3 client defaults are usually fine. If you see "bucket not found" while the bucket clearly exists, suspect virtual‑hosted DNS resolution and switch to path‑style via the SDK option (objectfs supports this via the s3_base_url being a plain hostname plus the client's default behaviour — verifiable empirically in prodtest before staging).
  • Signature v4. Garage requires v4. The AWS PHP SDK uses v4 by default. No action.
  • Multipart uploads. Supported by Garage. tool_objectfs uses multipart for large files automatically.
  • Object tagging. tool_objectfs has an "object tagging" feature for orphan tracking; Garage's S3 tag support has improved across 1.x but verify with aws s3api put-object-tagging against the public endpoint before relying on it. Safe to leave the feature off initially.
  • Replication. Production storage.reb.rw should be at least 3‑node, replication_factor = 3, distinct zones. The doc you already have covers this — make sure that's the actual deployed shape and not a single‑node install.

10. Decisions you need to make

  1. Pin commit vs branch. Pick: pin a specific commit on MOODLE_404_STABLE (recommended), or vendor a fork that has PR #691 merged. Either way, decide where the canonical pin lives — moodle-config.json is the natural place.
  2. Bucket scoping. One bucket per environment (moodle-staging, moodle) or one bucket with a per‑env key prefix? Per‑bucket is cleaner for IAM/quotas; per‑prefix saves operational overhead. Recommendation: per‑bucket.
  3. Phase B trigger. Who decides when staging is "stable enough" to flip deletelocal=1 there, and the same for prod? Suggest a checklist: 7+ days clean, <0.1% task failure rate, zero "missing object" reports, no admin escalations.
  4. Pre‑signed URL scope. Whitelist of extensions matters. Aggressive whitelisting (lots of types) maximises PHP offload but exposes more direct‑S3 access; conservative whitelisting (just mp4,mp3,zip,iso) catches 80% of bandwidth at near‑zero risk.
  5. Disposition of the existing prod_elearning_moodledata volume. Keep it (it'll shrink over time and still hold caches/sessions/temp) — but plan the eventual size budget. Probably 5–10 GB after drain instead of 83 GB.
